## 0. Resolved decisions (2026-07-11 review)

1. **Scope = full AI sales employee.** All milestones (M0–M9) build. Payment-chase path still lands first (M0–M4) because it is the highest-value slice, but nothing is parked.
2. **"Replies received" → "Chats imported"** in the Today brief. WhatsApp Business API integration is a later phase; when it lands, the metric upgrades back to true replies.
3. **Real billing at ₹999/mo — Razorpay + Stripe.** The fake-door paywall is replaced by a real subscription modal and server-verified entitlements (§6a, §7, milestone M8). One gateway abstraction, Razorpay wired first (Indian sellers, UPI), Stripe second behind the same interface. **Store-policy risk flagged in §15 — Apple/Google require IAP/Play Billing for in-app digital subscriptions; mitigation is web-based checkout, see risk table.**
4. **Order statuses follow the mock exactly.** Fulfillment enum becomes `confirmed / packed / shipped / delivered / cancelled` (existing `pending` rows migrate to `confirmed`; default `confirmed`). "Payment Pending"/"Paid" chips render from `payment_status`; the "Completed" tab maps to `delivered`.

### 0a. UI fidelity mandate

The mockups are the contract, not inspiration. Every screen is built pixel-faithful to the V1.0.0 image: exact palette (extracted hex committed to `AppColors` in M0), typography scale, radii, spacing, card layouts, chip styles, tab shapes, the robot illustration slots, and per-screen element order. Any deviation (platform constraint, missing asset, impossible interaction) is raised for sign-off before building around it — never silently redesigned.

## 0b. Amendment v3 — final-design deltas (2026-07-14, approved)

The final design (`docs/design/v1-final-design.png`) supersedes the earlier 13-screen mockup set as the visual contract. It adds surfaces the v2 TDD did not cover. Rulings below override earlier sections where they conflict; everything not mentioned stands unchanged.

### Scope rulings

1. **Team / multi-user → V2.** The Business ₹2,499/mo tier (multi-user, team members, WhatsApp API integration, API access) and the Invite Team Member screen are deferred. The whole schema is owner-scoped (`user_id` on every table + RLS); multi-user requires an org model and a rework of every policy and RPC — not a V1 add-on. The subscription screen keeps the mock's two-card layout: Pro ₹999 is the sole purchasable plan; the Business card renders static with a "Coming soon" tag and no checkout path (no fake door — no intent collection on a real-billing screen).
2. **Auth = phone OTP only, restyled.** Splash, welcome/login, and OTP-verify screens are rebuilt pixel-faithful to the mock **minus** the password field and Google/Apple buttons (mock is internally inconsistent — shows password and OTP for the same flow). Indian sellers are phone-first; social login adds Apple-signin obligations for zero validation value. Existing Supabase phone-OTP flow is kept.
3. **Business setup wizard (new screen).** "Let's set up your business" (name / type / category) runs once after first sign-in, writes `business_profile`, and is skipped when a profile exists. Progress dots per mock.
4. **Settings screen (new).** Reached from the Business hub. Functional rows only: Business Profile, Payment Methods, Invoice Settings, Notifications, Data & Privacy, Help & Support. Deferred-feature rows (Team Members, WhatsApp Integration, Automation) are omitted rather than rendered dead — "never fabricate" applies to navigation too. Rows return in V2 with their features.
5. **Payment screens consolidated.** The mock shows two payment-method screens (list-style and sheet-style). One `PaymentMethodSheet` implementation serves both contexts (order detail "Collect payment" and invoice "Send Payment Link"); visual style follows the sheet variant.

### Approved improvements beyond the mock

- **I1 — Quick-approve from card (M4).** Approval tiles on Today and My Work carry the action chip (Review & Send / Send Reminder / Create Order) per the mock; approving a drafted reply from the chip launches wa.me directly without opening the workspace first. Tapping the tile body still opens the workspace for review/edit. Cuts J1's taps-per-chase roughly in half; the human-approval gate is preserved (the chip *is* the approval).
- **I2 — OS share-target capture (M2 stretch).** Register the app as an Android share target (text + image) so a seller can share a WhatsApp screenshot or copied thread straight into the capture flow — no copy → switch app → tap + → paste dance. Falls out of M2 if the plugin integration fights the existing capture pipeline; ships in V1.1 at worst. iOS share extension deferred (heavier build surface).

### Milestone impact

- **MA — Auth & onboarding restyle** (new, small): splash + welcome + OTP restyle, setup wizard. Depends on M0 only; parallel-safe with anything. Ship before M9.
- Settings screen lands in **M9** (hardening) — mostly navigation to existing screens plus two static pages (Data & Privacy, Help & Support).
- I1 lands in **M4**, I2 in **M2** (stretch). All other milestones unchanged.

## 1. Overall architecture

Unchanged foundation, three new server-side capabilities, one client restructure.

```
┌───────────────────────── Flutter app (Riverpod 2, feature-first) ─────────────────────────┐
│  Today  │  My Work  │  Capture(+)  │  Orders  │  Business hub                              │
│  conversations · customers-360 · follow-up calendar · assistant chat · invoices · catalog  │
└──────────────┬─────────────────────────────────────────────────────────────────────────────┘
               │ supabase_flutter (anon key, RLS-scoped)            wa.me / tel: deep links →
               ▼
┌───────────────────────── Supabase (project dgviploqkwyuttcdnddq) ─────────────────────────┐
│ Postgres + RLS (deny-by-default)          Storage (private buckets, signed URLs)          │
│ existing: business_profile customers products leads orders order_items payments app_events│
│ new:      conversations messages ai_work_items follow_ups ai_summaries subscriptions     │
│ RPCs (security invoker): create_order_with_items v3 · record_payment · assign_invoice_    │
│   number · mark_order_delivered · check_ai_rate_limit · NEW read-only assistant RPCs      │
│                                                                                            │
│ Edge functions (Deno):                                                                     │
│   parse-enquiry   (exists — extend schema: budget, notes)                                  │
│   draft-reply     (new — suggested reply for a conversation)                               │
│   generate-work-items (new — batch: prioritize + draft; writes ai_work_items)              │
│   summarize-customer  (new — summary bullets, confidence, ai_facts)                        │
│   assistant       (new — Q&A over whitelisted read-only RPCs)                              │
│   create-checkout (new — Razorpay/Stripe session; JWT-authed)                              │
│   billing-webhook (new — gateway → subscriptions; signature-verified, service role)        │
│      all behind: JWT auth → input validation → shared rate limit → provider abstraction    │
└──────────────┬─────────────────────────────────────────────────────────────────────────────┘
               ▼
        Gemini 2.5 Flash (existing provider.ts abstraction; Claude adapter slot reserved)
```

Architectural invariants (carried from existing code, non-negotiable):

- **Human-in-the-loop everywhere.** AI drafts; the seller approves; sends happen via `wa.me` deep links from the seller's own WhatsApp. No autonomous outbound.
- **Amounts, UPI IDs, phone numbers always come from the database, never from model output.** LLMs write prose only. The client coercion layer (pattern of `AiParseService._coerce`) is the trust boundary for every new function.
- **RLS on every new table before it gets data**; all RPCs `security invoker`; service_role never in the app — its only server-side holder is `billing-webhook` (§6a).
- **AI is off the critical path.** Every AI call has a timeout and a non-AI fallback (rules parse, deterministic scoring, empty state). App is fully usable if all edge functions are down.
- **Telemetry is fire-and-forget, PII-free** (`EventService` pattern).

## 5. User journeys

**J1 — Morning chase (the Money Chaser core).**
Open app → Today brief shows "₹18,000 outstanding, 6 follow-ups prepared" → Start My Work → first item: "Rahul, payment pending ₹12,000 — Send Reminder" → tap → workspace opens with AI-drafted reminder (tone: seller's own; amount from `orders-payments`, never from the model) → Approve & Send → WhatsApp opens prefilled → back → item marked done → next item. Events: `brief_view`, `work_item_open`, `reply_approved`, `reply_sent`.

**J2 — Capture from a DM.**
Customer messages on Instagram → seller copies thread → + → Paste WhatsApp Chat → extraction progress (rules parse instant, AI refine ≤3s, staged animation covers latency) → Review & Confirm shows customer, product, budget ₹10,000, follow-up date, 92% confidence → Confirm & Save → conversation + enquiry + follow-up created → lands in My Work.

**J3 — Enquiry to paid order.**
Workspace chat tab → AI summary: "interested in Kundan set, budget ₹10k, asked discount" → suggested reply with price → approve & send → customer agrees (seller imports/reads reply) → Create Order from workspace → items pre-filled from enquiry, discount ₹500, expected date → Create → UPI collect link/QR → payment recorded (existing RPC) → order Paid → invoice one tap.

**J4 — Ask the assistant.**
Today → robot card → "How much money is pending?" → assistant runs whitelisted RPC `assistant_outstanding_summary` → answers with per-customer breakdown → "Create follow-up messages" → assistant returns drafts as proposed work items → seller approves each (nothing sends automatically).

**J5 — Weekly relationship pass.**
Business → Customers → Meena → 360: score 4.6, LTV ₹48,500, ₹8,000 outstanding, facts ("prefers evening replies", "birthday 18 Aug") → recent orders → tap chat → nudge drafted.

**J6 — Trial to paid.**
Day 15: work-item generation gated → subscription modal (₹999/mo, feature list) → Pay with UPI → `create-checkout` → Razorpay sheet → webhook activates → app resumes, `subscriptions` row `active`, AI features unlock. Events: `paywall_view`, `checkout_started`, `subscription_activated`.

## 6. Database changes

All additive (one exception: the status-enum rewrite in 0020, guarded by a data update); migrations `0017–0024` applied to project `dgviploqkwyuttcdnddq` only (MCP connector currently sees the wrong project — hand SQL to the SQL editor or `supabase db push` unless connectivity is fixed). Every table: RLS enabled in the same migration, owner-scoped policies, `set_updated_at` trigger where mutable.

### 0017 — conversations & messages

```sql
create table conversations (
  id uuid pk default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade,
  customer_id uuid not null references customers(id) on delete cascade,
  last_message_at timestamptz,
  created_at/updated_at timestamptz,
  unique (user_id, customer_id)          -- one thread per customer (V1)
);
create table messages (
  id uuid pk,
  user_id uuid not null,
  conversation_id uuid not null references conversations(id) on delete cascade,
  direction text check (direction in ('inbound','outbound')),
  source text check (source in ('paste','screenshot','voice','manual','ai_send')),
  body text not null,
  sent_at timestamptz,                   -- best-effort from import; else created_at
  meta jsonb default '{}',               -- e.g. {"approved_work_item": "..."}
  created_at timestamptz
);
-- indexes: (user_id, conversation_id, created_at); RLS: owner-only, messages immutable (no update policy)
```

`ai_send` = message the seller approved and launched via wa.me. Recorded optimistically at launch (we cannot confirm WhatsApp delivery); the timeline labels it "sent from Closr".

### 0018 — ai_work_items

```sql
create table ai_work_items (
  id uuid pk, user_id uuid not null,
  customer_id uuid references customers(id) on delete cascade,
  lead_id uuid references leads(id) on delete set null,
  order_id uuid references orders(id) on delete set null,
  kind text check (kind in ('reply','payment_reminder','create_order','invoice','follow_up','share_catalog')),
  priority text check (priority in ('high','medium','low')),
  score int not null default 0,          -- deterministic; drives ordering within priority
  title text not null,                   -- "Payment pending"
  context text,                          -- one-liner shown on card
  amount numeric(12,2),                  -- copied from DB aggregates at generation time
  draft jsonb default '{}',              -- {"message": "..."} prose only — never amounts
  confidence numeric(3,2),
  status text check (status in ('pending','approved','dismissed','expired','done')) default 'pending',
  batch_id uuid not null,                -- one generation run
  expires_at timestamptz,                -- stale items auto-hidden
  created_at/updated_at
);
-- index (user_id, status, priority, score desc); RLS owner-only
```

### 0019 — follow_ups (standalone, calendar-backed)

```sql
create table follow_ups (
  id uuid pk, user_id uuid not null,
  customer_id uuid not null references customers(id) on delete cascade,
  lead_id uuid references leads(id) on delete set null,
  due_at timestamptz not null,
  note text,
  kind text check (kind in ('reply','payment','general')) default 'general',
  status text check (status in ('pending','done','skipped')) default 'pending',
  created_at/updated_at
);
```

Backfill: one row per lead with `status='follow' and follow_up_date is not null`. Transition: notification engine and calendar read `follow_ups` only; capture writes `follow_ups` (and stops writing `leads.follow_up_date`); the lead columns stay for history and are dropped in a post-V1 cleanup migration.

### 0020 — orders: pricing & lifecycle

```sql
alter table orders
  add column discount numeric(12,2) not null default 0,
  add column shipping_fee numeric(12,2) not null default 0,
  add column expected_date date;
-- Status enum matches the mock exactly: pending renamed to confirmed.
update orders set status = 'confirmed' where status = 'pending';
alter table orders drop constraint orders_status_check;
alter table orders add constraint orders_status_check
  check (status in ('confirmed','packed','shipped','delivered','cancelled'));
alter table orders alter column status set default 'confirmed';
```

`grand_total = subtotal − discount + shipping_fee` (validated non-negative in RPC). New `create_order_with_items` **v3** adds `p_discount`, `p_shipping_fee`, `p_expected_date`; old signature dropped in the same migration (single client). New `cancel_order(p_order_id)` RPC: sets `cancelled`, releases a booked unique piece (`booked → available`), refuses when payments exist (returns error; refunds are out of scope for V1).

### 0021 — customer intelligence & ai summaries

```sql
alter table customers
  add column ai_facts jsonb not null default '[]',      -- [{"fact":"prefers evening replies","source_message_id":"..."}]
  add column birthday date,
  add column last_contact_at timestamptz;

create table ai_summaries (
  id uuid pk, user_id uuid not null,
  customer_id uuid not null references customers(id) on delete cascade,
  bullets jsonb not null default '[]',
  close_confidence numeric(3,2),
  source_hash text,                       -- hash of message ids summarized; skip regeneration when unchanged
  created_at timestamptz,
  unique (user_id, customer_id)
);

create view customer_stats with (security_invoker = true) as
  select c.id as customer_id, c.user_id,
         count(distinct o.id) filter (where o.status <> 'cancelled') as total_orders,
         coalesce(sum(o.grand_total) filter (where o.status <> 'cancelled'), 0) as lifetime_value,
         coalesce(sum(o.grand_total - paid.amt) filter (where o.status <> 'cancelled'), 0) as outstanding
  from customers c left join orders o ... left join lateral (sum payments) paid ...;
```

**Relationship score is computed, not stored**: deterministic Dart function over `customer_stats` + recency (orders count, repeat rate, payment promptness, recency of contact) → 0–5 with a documented formula and unit tests. No LLM. `ai_facts` are LLM-extracted but each fact keeps its source message id so the seller can see why.

### 0022 — leads: budget + capture confidence

```sql
alter table leads
  add column budget numeric(12,2),
  add column ai_confidence numeric(3,2);
```

### 0023 — shared AI rate limit

Generalize `check_ai_parse_rate_limit` → `check_ai_rate_limit(p_feature text, p_max int, p_window_seconds int)` with per-feature counters (parse 30/hr as today; draft-reply 60/hr; assistant 40/hr; work-items 6/hr; summarize 30/hr). Old function kept as a thin wrapper until parse-enquiry redeploys.

### 0024 — subscriptions (real billing)

```sql
create table subscriptions (
  id uuid pk default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade,
  plan text not null default 'pro_monthly',        -- ₹999/mo; single plan in V1
  status text not null check (status in ('trialing','active','past_due','cancelled','expired')),
  gateway text check (gateway in ('razorpay','stripe')),
  gateway_customer_id text,
  gateway_subscription_id text,
  current_period_end timestamptz,
  trial_end timestamptz,
  created_at/updated_at timestamptz,
  unique (user_id)
);
create table billing_events (                       -- webhook idempotency ledger
  id text primary key,                              -- gateway event id
  user_id uuid,
  gateway text not null,
  type text not null,
  payload jsonb not null,
  created_at timestamptz not null default now()
);
```

RLS: users can **select** their own subscription row; **no insert/update/delete policies for `authenticated`** — subscription state is written exclusively by the `billing-webhook` function using the service role (the one sanctioned service-role surface in the system; it never touches other tables). `billing_events` has no client policies at all. Trial: a `trialing` row (`trial_end = signup + 14 days`) is created on first entitlement check; after `trial_end` with no active gateway subscription, status flips to `expired` and AI features gate to the subscription modal (core data entry keeps working — the seller's data is never hostage).

## 7. API / Edge Function changes

All functions follow the `parse-enquiry` contract: JWT required → strict input validation before consuming a rate-limit slot → shared rate limit RPC → provider call with timeout → error labels only, never payload content in logs. Provider stays behind `createParser`-style factories (`AI_PROVIDER` env; Claude adapter slot reserved).

| Function | Method/input | Output | Notes |
|---|---|---|---|
| `parse-enquiry` (extend) | `{text?, image?}` | + `budget: number\|null`, `notes: string\|null` | responseSchema + prompt updated; client coercion extended (budget: positive number, capped 10⁷) |
| `draft-reply` (new) | `{customer_id, objective: 'reply'\|'payment_reminder'\|'follow_up'\|'nudge'}` | `{message, confidence}` | Server loads last N messages + enquiry + outstanding **from DB** (client sends ids, never amounts); prompt forbids inventing prices/UPI; output is prose only |
| `generate-work-items` (new) | `{}` (user-scoped) | `{batch_id, count}` | Two phases: (1) deterministic candidate query in SQL — overdue payments, due follow-ups, unanswered enquiries, invoiceable orders; scores computed in code; (2) one batched LLM call drafts message prose for the top ≤10 items. Writes `ai_work_items`, expires the previous batch. Invoked on app foreground with a 30-min client-side debounce |
| `summarize-customer` (new) | `{customer_id}` | `{bullets[], close_confidence, facts[]}` | Skips LLM when `source_hash` unchanged; upserts `ai_summaries`, merges new facts into `customers.ai_facts` (dedup by normalized text) |
| `assistant` (new) | `{question, customer_id?, history[≤10]}` | `{answer, suggestions[], proposed_work_items[]}` | LLM with **tool-use over whitelisted read-only RPCs only**: `assistant_outstanding_summary`, `assistant_top_customers`, `assistant_pipeline_stats`, `assistant_overdue_followups` (all security-invoker SQL, no free-form SQL ever). May *propose* work items; client confirms before insert. Single-turn tool loop, max 3 tool calls, 15s budget |
| `create-checkout` (new) | `{gateway: 'razorpay'\|'stripe'}` | `{checkout_url \| razorpay_subscription_id + key_id}` | JWT-authed. Creates the gateway customer + subscription (Razorpay Subscriptions API / Stripe Checkout session) for the single ₹999 plan; stores gateway ids on the user's subscription row (pending state). No amounts from the client — plan/price are server constants |
| `billing-webhook` (new) | Razorpay/Stripe webhook POST | 200/4xx | Deployed `--no-verify-jwt`; **auth = gateway signature verification** (`X-Razorpay-Signature` HMAC / `Stripe-Signature`) with per-gateway secrets. Idempotent via `billing_events` pk insert-or-skip. Handles: activated, charged/renewed, payment failed (→ `past_due`), cancelled, expired. Service role, writes only `subscriptions` + `billing_events` |

Billing client flow: subscription modal → `create-checkout` → Razorpay native SDK (`razorpay_flutter`) or Stripe Checkout in browser → gateway calls `billing-webhook` → app re-reads `subscriptions` on resume/realtime → entitlement unlocks. Client never sets entitlement state; UI reflects the DB row only.

Prompt-injection stance (applies to every function that reads imported chat text): imported messages are untrusted user input. System prompts instruct extraction/drafting only; no function has a write tool; the only actions in the product are client-side and human-approved. Model output is rendered as text, never interpolated into URLs except through the existing sanitized wa.me builder (digits-only phone from DB + URL-encoded body).

Stay on Riverpod 2 `StateNotifierProvider` (codebase-consistent; no codegen migration in V1 — mixing `@riverpod` codegen into a StateNotifier codebase mid-feature adds risk for zero user value).

```

  eventServiceProvider                    (exists)
  aiClientProvider                        (new — thin typed wrapper over functions.invoke, timeouts, coercion)
```

## 11. State management summary

- **Server state**: Supabase is the source of truth; providers fetch on entry + invalidate after mutations (existing pattern, e.g. orders reload on tab enter). No local DB/offline cache in V1.
- **Session state**: `last_seen_at` (brief delta window) and work-items debounce timestamp in `shared_preferences`.
- **Ephemeral state**: capture draft, create-order draft, assistant turns — autoDispose StateNotifiers.
- **Race handling**: token pattern from `CaptureController` (`_parseToken`) is the house style for any user-editable + AI-refined state (reused in draft-reply editing).
- **Optimistic updates**: work-item approve/dismiss and follow-up done flip locally then persist; rollback + snackbar on failure.

## 15. Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Scope: 13 screens + 4 new functions | Slip, half-built everything | Milestone gating; M0–M4 is the product; each M shippable |
| Brief overpromises ("AI worked while you were away" with no inbound channel) | Trust collapse on day 1 | Brief counts only real DB deltas; metric renames (Q#2); never fabricate activity |
| Prompt injection via imported chats | AI drafts attacker-influenced text | No write tools; human approval gate; amounts/UPI from DB only; render-as-text; security review in M8 |
| LLM cost/latency creep (5 functions) | ₹ burn, slow UX | Per-feature rate limits (0023), `ai_call` telemetry, source_hash caching, batched drafting, Flash-tier model |
| Deterministic scoring feels dumb vs mock's "AI prioritized" | Feature feels fake | Scores use real ₹ + dates (defensible); context lines LLM-polished; iterate on formula with telemetry |
| follow_ups migration breaks notification engine | Missed reminders (core promise) | Dual-read window, backfill test, engine unit tests before cutover |
| wa.me sends unconfirmable | "Sent" state may be false | Label as "opened in WhatsApp"; timeline wording honest |
| MCP connected to wrong Supabase project | Migration lands in wrong DB | Hard rule: verify `list_projects` shows dgviploqkwyuttcdnddq or apply by hand; never venora |
| RPC signature change (v3) vs deployed clients | Old app versions break on order create | Drop-and-replace only while user count ≈ concierge cohort; after launch, additive-only RPC versioning |
| **Store policy: in-app digital subscription sold via Razorpay/Stripe** | Apple (IAP mandate) and Google (Play Billing mandate) can reject or pull the app | Decide distribution posture in M8: (a) web-based checkout opened in browser + externally-purchased account state (Netflix/Spotify "reader" pattern — still restricted for non-reader apps), (b) Play Billing/StoreKit added later, (c) India-first Android sideload/UPI leniency. | Dual gateway (Razorpay + Stripe) doubles billing surface | Slip in M8 | Single `_shared/billing` interface; Razorpay ships first and gates the milestone; Stripe follows behind the same interface without schema change |

## 16. Migration strategy

**Database:** migrations 0017–0024, one concern each, RLS + policies in the same file as the table, advisors run after each. Backfills (`follow_ups` from leads; `conversations` seeded from existing `leads.message` + screenshots as one inbound message each) are idempotent inserts guarded by `not exists`. Rollback = new forward migration (house style: forward-only, see 0011).

**Code:** strangler pattern per feature — new feature folder ships behind the new nav, legacy screen deleted in the same milestone its replacement lands (M0 kills Dashboard; M4 kills EnquiriesScreen, `leadsControllerProvider`, `fetchLegacyMaps`, legacy NotificationsScreen). No feature flags: pre-launch app, one cohort, milestone = release.

**Edge functions:** `parse-enquiry` schema change is backward-compatible (new nullable fields). New functions deploy dark ahead of their client milestone. Secrets: existing `GEMINI_API_KEY` reused; M8 adds `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, `RAZORPAY_WEBHOOK_SECRET`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET` — Supabase function secrets only, never in the app bundle or git.

**Data safety:** no destructive column drops in V1; `leads.follow_up_date`/`follow_up_note` retained (read-only) until a post-V1 cleanup migration after one clean release cycle.

**Verification per milestone:** `flutter analyze` → `flutter test` → manual journey J1–J6 subset → Supabase advisors → code-review agent; security-reviewer agent on M1 (RLS), M3/M7 (AI functions), M8 (billing: webhook auth, entitlement bypass, secrets), M9 (full pass).
