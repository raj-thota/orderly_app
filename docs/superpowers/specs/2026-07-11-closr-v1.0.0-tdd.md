## 0. Open questions (must be answered before lock)

These change scope; everything else in this document is designed to survive any answer.

1. **Money Chaser vs full V1.** The 2026-07-11 direction memo says the product is the Money Chaser (payment recovery, ₹999/mo). The V1.0.0 mockups show the full AI-sales-employee. This TDD treats payment chasing as the highest-priority work-item type and orders milestones so the chase path ships first — but if Money Chaser is the only Phase 1 deliverable, milestones M6–M8 should be deferred, not built. **Decision needed.**
2. **"Replies received" brief metric.** Without the WhatsApp Business API there is no inbound channel; the app cannot know a customer replied unless the seller imports the chat. Options: (a) drop the metric, (b) rename to "chats imported", (c) defer to a WhatsApp API phase. This TDD assumes (b).
3. **Paywall price.** Fake-door currently tests ₹299; direction memo says ₹999 with trial after the Audit moment. This TDD assumes ₹999 and keeps the fake door (no billing in V1).
4. **Order status "Confirmed" chip** in the Orders mockup. Existing enum is `pending/packed/shipped/delivered`. This TDD adds `cancelled` (mockup shows it) and renders `pending` as "Confirmed" once the order exists — no new `confirmed` state. Flag if a real confirmed/unconfirmed distinction is wanted.

## 1. Overall architecture

Unchanged foundation, three new server-side capabilities, one client restructure.

```
┌───────────────────────── Flutter app (Riverpod 2, feature-first) ─────────────────────────┐
│  Today  │  My Work  │  Capture(+)  │  Orders  │  Business hub                              │
│  conversations · customers-360 · follow-up calendar · assistant chat · invoices · catalog  │
└──────────────┬─────────────────────────────────────────────────────────────────────────────┘
               │ supabase_flutter (anon key, RLS-scoped)            wa.me / tel: deep links →
               ▼
┌───────────────────────── Supabase (project dgviploqkwyuttcdnddq) ─────────────────────────┐
│ Postgres + RLS (deny-by-default)          Storage (private buckets, signed URLs)          │
│ existing: business_profile customers products leads orders order_items payments app_events│
│ new:      conversations messages ai_work_items follow_ups ai_summaries                    │
│ RPCs (security invoker): create_order_with_items v3 · record_payment · assign_invoice_    │
│   number · mark_order_delivered · check_ai_rate_limit · NEW read-only assistant RPCs      │
│                                                                                            │
│ Edge functions (Deno):                                                                     │
│   parse-enquiry   (exists — extend schema: budget, notes)                                  │
│   draft-reply     (new — suggested reply for a conversation)                               │
│   generate-work-items (new — batch: prioritize + draft; writes ai_work_items)              │
│   summarize-customer  (new — summary bullets, confidence, ai_facts)                        │
│   assistant       (new — Q&A over whitelisted read-only RPCs)                              │
│      all behind: JWT auth → input validation → shared rate limit → provider abstraction    │
└──────────────┬─────────────────────────────────────────────────────────────────────────────┘
               ▼
        Gemini 2.5 Flash (existing provider.ts abstraction; Claude adapter slot reserved)
```

Architectural invariants (carried from existing code, non-negotiable):

- **Human-in-the-loop everywhere.** AI drafts; the seller approves; sends happen via `wa.me` deep links from the seller's own WhatsApp. No autonomous outbound.
- **Amounts, UPI IDs, phone numbers always come from the database, never from model output.** LLMs write prose only. The client coercion layer (pattern of `AiParseService._coerce`) is the trust boundary for every new function.
- **RLS on every new table before it gets data**; all RPCs `security invoker`; no service_role in the app.
- **AI is off the critical path.** Every AI call has a timeout and a non-AI fallback (rules parse, deterministic scoring, empty state). App is fully usable if all edge functions are down.
- **Telemetry is fire-and-forget, PII-free** (`EventService` pattern).

## 5. User journeys

**J1 — Morning chase (the Money Chaser core).**
Open app → Today brief shows "₹18,000 outstanding, 6 follow-ups prepared" → Start My Work → first item: "Rahul, payment pending ₹12,000 — Send Reminder" → tap → workspace opens with AI-drafted reminder (tone: seller's own; amount from `orders-payments`, never from the model) → Approve & Send → WhatsApp opens prefilled → back → item marked done → next item. Events: `brief_view`, `work_item_open`, `reply_approved`, `reply_sent`.

**J2 — Capture from a DM.**
Customer messages on Instagram → seller copies thread → + → Paste WhatsApp Chat → extraction progress (rules parse instant, AI refine ≤3s, staged animation covers latency) → Review & Confirm shows customer, product, budget ₹10,000, follow-up date, 92% confidence → Confirm & Save → conversation + enquiry + follow-up created → lands in My Work.

**J3 — Enquiry to paid order.**
Workspace chat tab → AI summary: "interested in Kundan set, budget ₹10k, asked discount" → suggested reply with price → approve & send → customer agrees (seller imports/reads reply) → Create Order from workspace → items pre-filled from enquiry, discount ₹500, expected date → Create → UPI collect link/QR → payment recorded (existing RPC) → order Paid → invoice one tap.

**J4 — Ask the assistant.**
Today → robot card → "How much money is pending?" → assistant runs whitelisted RPC `assistant_outstanding_summary` → answers with per-customer breakdown → "Create follow-up messages" → assistant returns drafts as proposed work items → seller approves each (nothing sends automatically).

**J5 — Weekly relationship pass.**
Business → Customers → Meena → 360: score 4.6, LTV ₹48,500, ₹8,000 outstanding, facts ("prefers evening replies", "birthday 18 Aug") → recent orders → tap chat → nudge drafted.

## 6. Database changes

All additive; migrations `0017+` applied to project `dgviploqkwyuttcdnddq` only (MCP connector currently sees the wrong project — hand SQL to the SQL editor or `supabase db push` unless connectivity is fixed). Every table: RLS enabled in the same migration, owner-scoped policies, `set_updated_at` trigger where mutable.

### 0017 — conversations & messages

```sql
create table conversations (
  id uuid pk default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade,
  customer_id uuid not null references customers(id) on delete cascade,
  last_message_at timestamptz,
  created_at/updated_at timestamptz,
  unique (user_id, customer_id)          -- one thread per customer (V1)
);
create table messages (
  id uuid pk,
  user_id uuid not null,
  conversation_id uuid not null references conversations(id) on delete cascade,
  direction text check (direction in ('inbound','outbound')),
  source text check (source in ('paste','screenshot','voice','manual','ai_send')),
  body text not null,
  sent_at timestamptz,                   -- best-effort from import; else created_at
  meta jsonb default '{}',               -- e.g. {"approved_work_item": "..."}
  created_at timestamptz
);
-- indexes: (user_id, conversation_id, created_at); RLS: owner-only, messages immutable (no update policy)
```

`ai_send` = message the seller approved and launched via wa.me. Recorded optimistically at launch (we cannot confirm WhatsApp delivery); the timeline labels it "sent from Closr".

### 0018 — ai_work_items

```sql
create table ai_work_items (
  id uuid pk, user_id uuid not null,
  customer_id uuid references customers(id) on delete cascade,
  lead_id uuid references leads(id) on delete set null,
  order_id uuid references orders(id) on delete set null,
  kind text check (kind in ('reply','payment_reminder','create_order','invoice','follow_up','share_catalog')),
  priority text check (priority in ('high','medium','low')),
  score int not null default 0,          -- deterministic; drives ordering within priority
  title text not null,                   -- "Payment pending"
  context text,                          -- one-liner shown on card
  amount numeric(12,2),                  -- copied from DB aggregates at generation time
  draft jsonb default '{}',              -- {"message": "..."} prose only — never amounts
  confidence numeric(3,2),
  status text check (status in ('pending','approved','dismissed','expired','done')) default 'pending',
  batch_id uuid not null,                -- one generation run
  expires_at timestamptz,                -- stale items auto-hidden
  created_at/updated_at
);
-- index (user_id, status, priority, score desc); RLS owner-only
```

### 0019 — follow_ups (standalone, calendar-backed)

```sql
create table follow_ups (
  id uuid pk, user_id uuid not null,
  customer_id uuid not null references customers(id) on delete cascade,
  lead_id uuid references leads(id) on delete set null,
  due_at timestamptz not null,
  note text,
  kind text check (kind in ('reply','payment','general')) default 'general',
  status text check (status in ('pending','done','skipped')) default 'pending',
  created_at/updated_at
);
```

Backfill: one row per lead with `status='follow' and follow_up_date is not null`. Transition: notification engine and calendar read `follow_ups` only; capture writes `follow_ups` (and stops writing `leads.follow_up_date`); the lead columns stay for history and are dropped in a post-V1 cleanup migration.

### 0020 — orders: pricing & lifecycle

```sql
alter table orders
  add column discount numeric(12,2) not null default 0,
  add column shipping_fee numeric(12,2) not null default 0,
  add column expected_date date;
alter table orders drop constraint orders_status_check;
alter table orders add constraint orders_status_check
  check (status in ('pending','packed','shipped','delivered','cancelled'));
```

`grand_total = subtotal − discount + shipping_fee` (validated non-negative in RPC). New `create_order_with_items` **v3** adds `p_discount`, `p_shipping_fee`, `p_expected_date`; old signature dropped in the same migration (single client). New `cancel_order(p_order_id)` RPC: sets `cancelled`, releases a booked unique piece (`booked → available`), refuses when payments exist (returns error; refunds are out of scope for V1).

### 0021 — customer intelligence & ai summaries

```sql
alter table customers
  add column ai_facts jsonb not null default '[]',      -- [{"fact":"prefers evening replies","source_message_id":"..."}]
  add column birthday date,
  add column last_contact_at timestamptz;

create table ai_summaries (
  id uuid pk, user_id uuid not null,
  customer_id uuid not null references customers(id) on delete cascade,
  bullets jsonb not null default '[]',
  close_confidence numeric(3,2),
  source_hash text,                       -- hash of message ids summarized; skip regeneration when unchanged
  created_at timestamptz,
  unique (user_id, customer_id)
);

create view customer_stats with (security_invoker = true) as
  select c.id as customer_id, c.user_id,
         count(distinct o.id) filter (where o.status <> 'cancelled') as total_orders,
         coalesce(sum(o.grand_total) filter (where o.status <> 'cancelled'), 0) as lifetime_value,
         coalesce(sum(o.grand_total - paid.amt) filter (where o.status <> 'cancelled'), 0) as outstanding
  from customers c left join orders o ... left join lateral (sum payments) paid ...;
```

**Relationship score is computed, not stored**: deterministic Dart function over `customer_stats` + recency (orders count, repeat rate, payment promptness, recency of contact) → 0–5 with a documented formula and unit tests. No LLM. `ai_facts` are LLM-extracted but each fact keeps its source message id so the seller can see why.

### 0022 — leads: budget + capture confidence

```sql
alter table leads
  add column budget numeric(12,2),
  add column ai_confidence numeric(3,2);
```

### 0023 — shared AI rate limit

Generalize `check_ai_parse_rate_limit` → `check_ai_rate_limit(p_feature text, p_max int, p_window_seconds int)` with per-feature counters (parse 30/hr as today; draft-reply 60/hr; assistant 40/hr; work-items 6/hr; summarize 30/hr). Old function kept as a thin wrapper until parse-enquiry redeploys.

## 7. API / Edge Function changes

All functions follow the `parse-enquiry` contract: JWT required → strict input validation before consuming a rate-limit slot → shared rate limit RPC → provider call with timeout → error labels only, never payload content in logs. Provider stays behind `createParser`-style factories (`AI_PROVIDER` env; Claude adapter slot reserved).

| Function | Method/input | Output | Notes |
|---|---|---|---|
| `parse-enquiry` (extend) | `{text?, image?}` | + `budget: number\|null`, `notes: string\|null` | responseSchema + prompt updated; client coercion extended (budget: positive number, capped 10⁷) |
| `draft-reply` (new) | `{customer_id, objective: 'reply'\|'payment_reminder'\|'follow_up'\|'nudge'}` | `{message, confidence}` | Server loads last N messages + enquiry + outstanding **from DB** (client sends ids, never amounts); prompt forbids inventing prices/UPI; output is prose only |
| `generate-work-items` (new) | `{}` (user-scoped) | `{batch_id, count}` | Two phases: (1) deterministic candidate query in SQL — overdue payments, due follow-ups, unanswered enquiries, invoiceable orders; scores computed in code; (2) one batched LLM call drafts message prose for the top ≤10 items. Writes `ai_work_items`, expires the previous batch. Invoked on app foreground with a 30-min client-side debounce |
| `summarize-customer` (new) | `{customer_id}` | `{bullets[], close_confidence, facts[]}` | Skips LLM when `source_hash` unchanged; upserts `ai_summaries`, merges new facts into `customers.ai_facts` (dedup by normalized text) |
| `assistant` (new) | `{question, customer_id?, history[≤10]}` | `{answer, suggestions[], proposed_work_items[]}` | LLM with **tool-use over whitelisted read-only RPCs only**: `assistant_outstanding_summary`, `assistant_top_customers`, `assistant_pipeline_stats`, `assistant_overdue_followups` (all security-invoker SQL, no free-form SQL ever). May *propose* work items; client confirms before insert. Single-turn tool loop, max 3 tool calls, 15s budget |

Prompt-injection stance (applies to every function that reads imported chat text): imported messages are untrusted user input. System prompts instruct extraction/drafting only; no function has a write tool; the only actions in the product are client-side and human-approved. Model output is rendered as text, never interpolated into URLs except through the existing sanitized wa.me builder (digits-only phone from DB + URL-encoded body).

## 8. Riverpod architecture

Stay on Riverpod 2 `StateNotifierProvider` (codebase-consistent; no codegen migration in V1 — mixing `@riverpod` codegen into a StateNotifier codebase mid-feature adds risk for zero user value).

```
core/
  eventServiceProvider                    (exists)
  aiClientProvider                        (new — thin typed wrapper over functions.invoke, timeouts, coercion)

features/
  today/       todayBriefProvider         FutureProvider<TodayBrief>      — DB deltas since last_seen_at (shared_prefs)
               approvalsProvider          StateNotifier<AsyncValue<List<WorkItem>>> — filtered view of work items
  work/        workItemsProvider          StateNotifier — list + approve/dismiss/done mutations (optimistic)
               workItemGeneratorProvider  — debounced trigger of generate-work-items on foreground
  capture/     captureControllerProvider  (exists, moves) + voiceCaptureProvider (speech_to_text session)
  conversations/ conversationProvider(customerId)  — messages stream + import/append
               customerSummaryProvider(customerId) — ai_summaries row + refresh via summarize-customer
               draftReplyProvider(customerId)      — request/approve lifecycle
  customers/   customerStatsProvider(customerId)   — customer_stats view row
               relationshipScoreProvider(customerId) — pure derivation (Provider.family)
  followups/   followUpCalendarProvider(weekStart) — follow_ups by day + mutations
  orders/      ordersControllerProvider (exists) + createOrderControllerProvider (draft state, totals math client-mirrored, server-authoritative)
  assistant/   assistantChatProvider      StateNotifier<AssistantState> — turns, pending tool status, proposed items
```

Rules carried over: services own Supabase calls (constructor-injectable for tests, as `EventService`/`AiParseService` do); controllers own state machines; screens are dumb consumers; every AI provider resolves to a fallback value on timeout, never an error state that blocks the flow.

## 11. State management summary

- **Server state**: Supabase is the source of truth; providers fetch on entry + invalidate after mutations (existing pattern, e.g. orders reload on tab enter). No local DB/offline cache in V1.
- **Session state**: `last_seen_at` (brief delta window) and work-items debounce timestamp in `shared_preferences`.
- **Ephemeral state**: capture draft, create-order draft, assistant turns — autoDispose StateNotifiers.
- **Race handling**: token pattern from `CaptureController` (`_parseToken`) is the house style for any user-editable + AI-refined state (reused in draft-reply editing).
- **Optimistic updates**: work-item approve/dismiss and follow-up done flip locally then persist; rollback + snackbar on failure.

## 16. Migration strategy

**Database:** additive-only migrations 0017–0023, one concern each, RLS + policies in the same file as the table, advisors run after each. Backfills (`follow_ups` from leads; `conversations` seeded from existing `leads.message` + screenshots as one inbound message each) are idempotent inserts guarded by `not exists`. Rollback = new forward migration (house style: forward-only, see 0011).

**Code:** strangler pattern per feature — new feature folder ships behind the new nav, legacy screen deleted in the same milestone its replacement lands (M0 kills Dashboard; M4 kills EnquiriesScreen, `leadsControllerProvider`, `fetchLegacyMaps`, legacy NotificationsScreen). No feature flags: pre-launch app, one cohort, milestone = release.

**Edge functions:** `parse-enquiry` schema change is backward-compatible (new nullable fields). New functions deploy dark ahead of their client milestone. Secrets: existing `GEMINI_API_KEY` reused; no new secret classes.

**Data safety:** no destructive column drops in V1; `leads.follow_up_date`/`follow_up_note` retained (read-only) until a post-V1 cleanup migration after one clean release cycle.

**Verification per milestone:** `flutter analyze` → `flutter test` → manual journey J1–J5 subset → Supabase advisors → code-review agent; security-reviewer agent on M1 (RLS), M3/M7 (AI functions), M8 (full pass).
